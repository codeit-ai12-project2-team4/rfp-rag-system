## 1. 전처리본 고르기 — 팀원 것이 이겼다

`documents.jsonl`(우리, olefile 직접 파싱)과 `cleaned_documents.jsonl`(팀원, hwp_raw)
둘을 같은 질문 세트로 나란히 쟀다.

| | documents | cleaned_documents |
|---|---|---|
| 본문 합계 | 11,207,023자 | 8,743,663자 (78%) |
| 중앙값 | 102,623자 | 80,129자 |

**본문이 22% 적은데 거의 모든 청킹 설정에서 이긴다** (최대 +0.216). 지운 2.5M자는
노이즈였다. boilerplate·플레이스홀더 제거가 효과가 있었다.

### 함정 — doc_id 가 안 맞아 비교가 35/100 만 됐다

`make_doc_id` 가 `{공고번호}-{공고차수}` 를 만드는데, pandas 가 공고번호 컬럼에
빈칸이 있으면 float 로 읽어 `20240330003.0-0` 이 된다. 팀원 쪽은 문자열이라
`20240330003-0`. `tidy_doc_id()` 로 `.0` 을 떼서 **82/100** 이 됐다.

두 형식을 한 함수로 읽는다 — `load_documents("cleaned_documents")`.
`from_langchain()` 이 `{page_content, metadata}` 를 우리 꼴로 맞춘다.

## 2. 청킹 — 지표가 큰 청크에 유리했다

처음 결과는 "클수록 좋다"였다 (recursive/1500/200 적중률@5 0.986).

**그런데 적중률@k 는 청크가 크면 그냥 오른다.** 극단적으로 문서 하나를 청크
하나로 만들면 1.0 이 된다. 개수로 비교하면 큰 쪽이 무조건 이긴다.

그래서 **글자 예산**으로 바꿨다 (`score_all(budget=6000)`, `settings.MAX_CONTEXT_CHARS`).
상위 k개 대신 6,000자에 들어가는 만큼을 본다. 생성 단계가 실제로 받는 것도
개수가 아니라 글자 수다.

바꾸니 적중률이 0.833~0.875 로 평평해지고 **MRR 이 갈렸다.**

### 그리고 청킹 결론이 한 번 더 뒤집혔다

| 질문 세트 | 이긴 설정 |
|---|---|
| 쉬운 세트(라벨 인용) | recursive/3000/400 |
| 어려운 세트 | **recursive/1200/200** |

section 방식은 전 설정에서 recursive 에 진다. BM25 만 큰 청크를 좋아한다.

## 3. 평가 세트 — 쉬운 질문으로는 아무것도 못 고른다

정규식이 라벨을 그대로 인용해 만든 질문("과업기간은?")으로는 일곱 설정이 전부
**0.88~0.99 로 뭉쳤다.** 86문항에서 상위 5개가 1~2문항 차이 = 노이즈.

`make_hard_pairs()` 로 유형별 세트를 만들었다 (`data/eval_qa.json`, 133문항).

| 유형 | 무엇 | 40문항 |
|---|---|---|
| 요구사항 | ID로 묻고 명칭을 답한다 | 표 한 줄을 정확히 찾아야 한다 |
| 배점 | 항목 이름으로 묻고 점수를 답한다 | 평가표 안을 찾아야 한다 |
| 의역 | 라벨 단어를 안 쓰고 묻는다 | "돈이 얼마나 드나" ← 본문은 "사업예산" |
| 없음 | 문서에 없는 것을 묻는다 (13문항) | 물러서야 정답. 검색 지표 제외 |

정답을 원문에서 뽑으므로 라벨링이 필요 없다. 만들자마자 BM25 가 0.965 → 0.050~0.550
으로 떨어졌다. **포화가 풀렸다.**

## 4. 검색 방법 — 머리말과 리랭커가 승패를 가른다

`cleaned_documents` + `recursive/1200/200`, 예산 6,000자, TEI BGE-m3.

```
설정                      배점   요구사항   의역
BM25                     0.050  0.500  0.550
Dense                    0.175  0.725  0.550
Dense+머리말               0.575  0.925  0.475
Dense+머리말+Rerank        0.950  0.975  0.675   ← 채택
Dense+머리말+Rerank+Widen  0.950  1.000  0.550
Hybrid                   0.100  0.775  0.550
Hybrid+Rerank            0.400  0.725  0.575
Hybrid+머리말              0.300  0.825  0.575
```

**머리말(`[사업명]`)은 Dense 에 결정적이다.** 배점 0.175 → 0.575.
공고를 하나로 좁혀서(`--scoped`) 재도 차이가 그대로라, 단순히 "그 공고로
몰아주는" 효과가 아니다.

**BM25 를 섞으면 망친다.** RRF 는 순위 융합이라, 배점에서 0.050 밖에 못 찾는
BM25 가 엉뚱한 청크를 올리면 Dense 의 좋은 1등이 밀린다.

**리랭커가 승패를 가른다.** 0.575 → 0.950. 쉬운 세트에서는 0.984 → 0.982 로
아무 일도 안 했다. 어려운 질문에서만 값을 한다. 3배 느리다(0.42 → 1.2초/질문).

**`Widen` 은 안 넣는다.** 요구사항을 1.000 으로 올리지만(표가 청크 경계에서
갈리는 걸 뒤 청크로 메운다) 의역을 0.675 → 0.550 으로 깎는다. 뒤 청크가 예산을
먹어 리랭커가 고른 상위 청크를 밀어내기 때문이다. 표 질문 전용 옵션으로 남긴다.

## 5. 목차가 검색을 오염시켰다 — 세 번 헛짚었다

**증상:** `"그럼 참가자격은?"` 에 목차 청크가 1위. `4. 세부 작성지침爜ȃ35 …` —
글자는 걸리는데 답은 쪽번호뿐이다. 목차에는 모든 절 제목이 모여 있어 **어떤
질문에도 걸린다.**

**신호:** 라틴확장B(U+0180~U+024F). 한글 목차의 점선·쪽번호가 필드 코드라 글자로
뽑으면 이 영역으로 샌다. 9,081개 중 103개(1.1%)가 5자 이상. 전부 목차였다.

### 헛짚음 1 — 문서 단위 `drop_toc`

`preprocessing.drop_toc` 을 문서에 돌렸더니 **8,743,663자 → 200자.**
`cleaned_documents` 는 칸마다 줄이 나뉜 형식이라 문서 전체를 목차로 본다.
우리 `documents.jsonl` 에서는 멀쩡히 돌던 코드다.

### 헛짚음 2 — 청크를 통째로 버림

문서 첫 청크는 보통 `표지 + 사업개요 표 + 목차` 한 덩어리다. 통째로 버렸더니
**의역 정답 17개**(`49,500천원`, `900,000,000원` …)가 같이 사라져 적중률이
0.550 → 0.175 로 무너졌다.

### 헛짚음 3 — 엉뚱한 범인 지목

`strip_toc_leaders` 를 범인으로 지목했다. 그것도 문제이긴 하다 —
`[⺀-鿿]?[ƀ-ʯ]+\s*\d*` 의 `\s*\d*` 가 라틴확장 뒤의 **진짜 숫자까지** 먹는다
(`사업예산籄ȃ 49,500천원` → `사업예산 ,500천원`). 하지만 빼도 26/40 그대로였다.
주범은 청크를 버린 쪽이었다.

### 최종 — 목차 **줄**만 지운다

```
목차 줄 정리: 100개 청크에서 목차만 걷어냄 · 3개는 목차뿐이라 버림
의역 40/40 · 배점 40/40 · 요구사항 40/40
```

**교훈:** 청킹이나 정제를 건드리면 지표를 재기 전에 **정답이 청크에 살아 있는지
먼저 센다.** 10초짜리 검사인데 이게 있었으면 세 번 헛짚지 않았다. 모든 설정이
같이 떨어지면 검색이 아니라 데이터를 의심해야 한다.
`compare_retrieval.py` 가 이제 매번 먼저 찍는다.

## 6. 그 밖에 배운 것

**리랭커 점수의 절대값에 의미를 두지 말 것.** 같은 문서·같은 파이프라인에서
질의 표현만 바꿔도 1위 점수가 1.0000 ↔ 0.0039 로 움직인다. 그런데 **고르는
청크는 셋 다 같았다.** 순위만 보면 된다. 하한선을 두고 자르면 답이 있는데도 버린다.

**미리보기는 질의어 주변을 보여줄 것.** 앞 160자만 보여주다가 정답 청크를 두 번
"엉뚱하다"고 오판했다. 1,200자 청크에서 답은 뒤쪽에 있을 수 있다.

**`except Exception` 을 기계적으로 좁히면 폴백이 죽는다.** 로컬에서 `except
Exception` → `except RuntimeError` 로 바뀌면서 네 곳이 조용히 죽었다.
실제 예외는 `ImportError`(kiwipiepy 없음), `FileNotFoundError`(맥엔
`/proc/meminfo` 없음), `ConnectionError`(서버 없음), OpenAI 예외였다.

**실제 UI 질문은 평가 질문보다 훨씬 짧다.** 133문항 0.95 를 찍고도 실사용 질문
세 개 중 하나가 깨졌다. 지표는 지표고, 눈으로 던져보는 건 따로 해야 한다.

## 최종 설정

```python
cleaned_documents
  → recursive/1200/200, 목차 줄 제거, 머리말([사업명]) 붙임
  → TEI BGE-m3 임베딩 (8085)
  → Dense(k=30) → Rerank(TEI bge-reranker-v2-m3-ko, 8086, k=8)
  → 6,000자 예산으로 자름
```

```bash
python src/preprocessing/run.py
python src/chunking.py --docs cleaned_documents --how recursive --size 1200 --overlap 200 --header
python src/vectorstore.py --chunks cleaned_documents__recursive_1200_200__header
```

```python
from src.retriever import retrieve_context, search_notices
context = retrieve_context(질문, doc_ids=["20240330003-0"])   # 공고 안에서
notices = search_notices("클라우드 전환", min_budget=300_000_000)  # 공고 찾기
```

## 아직 안 잰 것

- **`search_notices` 성능.** 공고 랭킹 정답 세트가 없다. 돌아가긴 하지만
  얼마나 잘하는지는 모른다. 쟀다고 말하면 안 된다.
- **대화 이어짐.** "그럼 참가자격은?" 은 목차를 치우고 나아졌지만 안 쟀다.
- **의역 유형이 0.675 천장.** 다른 유형이 0.95 를 찍는데 여기만 안 오른다.
