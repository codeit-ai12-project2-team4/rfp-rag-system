# 입찰메이트 수집 크론.  설치:  crontab docker/crontab.txt
#                       확인:  crontab -l
#                       로그:  tail -f /tmp/crawl.log
#
# 절대경로로 쓴다 — 크론은 PATH 도 가상환경도 물려받지 않는다. `python` 이라고
# 쓰면 시스템 파이썬이 잡혀서 "ModuleNotFoundError: lancedb" 로 조용히 실패한다.

SHELL=/bin/bash
HOME=/home/spai1203

# 업무시간에 3시간마다. 4시간을 되돌아봐서 **일부러 겹치게** 한다.
# 겹쳐도 이미 가진 doc_id 는 건너뛰므로, 마지막 실행 시각을 적어둘 상태 파일이
# 필요 없다. 상태 파일은 크론이 한 번 실패하면 그 구간이 영영 구멍으로 남는다.
0 12,15,18,21,0 * * * cd $HOME/rfp-rag-system && .venv/bin/python src/crawl.py --hours 4 >> /tmp/crawl.log 2>&1

# 새벽에 이틀치를 다시 훑는다. 낮에 놓친 것(공고 수정·지연 등록)을 메운다.
30 3 * * * cd $HOME/rfp-rag-system && .venv/bin/python src/crawl.py --days 2 >> /tmp/crawl.log 2>&1

# 로그가 무한정 자라지 않게. 일요일 새벽에 자른다.
0 4 * * 0 : > /tmp/crawl.log

# --- 수집 → 전처리 → 색인 → 재시작 -----------------------------------------
#
# 새벽 크롤링이 끝난 뒤에 돈다(3:30 시작, 45분이면 넉넉). prepare.py 가
# `--service` 라서 [1]전처리본 [2]청크 [3]인덱스까지만 본다. 평가 세트는
# API 가 안 읽고, 없다고 ok=False 가 되면 `&&` 가 막혀 반영이 안 된다.
#
# 청크는 `run_pipeline` 이 `cfg.CHUNKS` 경로에 직접 쓴다. `ingest.py` 를 따로
# 부를 필요가 없다 — 그건 외부에서 받은 청크 파일을 가져올 때 쓰는 경로다.
# 전처리본·청크·인덱스·평가세트를 순서대로 보고 없는 것만 만든다.
# 새 공고가 없으면 전부 O 로 지나가고 몇 초에 끝난다.
#
# **STORE=lance 는 .env 에 있으므로 여기 안 적는다.** 두 군데 적으면 한쪽만
# 고치게 된다. prepare.py 가 .env 를 읽어 lance 쪽만 검사·생성한다.
45 3 * * * cd $HOME/rfp-rag-system && .venv/bin/python scripts/retrieval/prepare.py --build --service >> /tmp/index.log 2>&1 && curl -fsS -X POST -H "x-api-token: $(grep '^API_TOKEN=' .env | cut -d= -f2-)" http://localhost:8010/reload >> /tmp/index.log 2>&1

0 4 * * 0 : > /tmp/index.log

# 왜 재시작이 아니라 /reload 인가 (9/9 변경)
#
# API 가 인덱스를 lru_cache 로 물고 있어서 새로 만들어도 그냥은 새 공고를 못 본다.
# 전에는 그래서 `sudo systemctl restart` 를 붙였다. 기동에 2분 반이 걸렸는데,
# 그 2분 반의 정체는 BM25 형태소 분석이었다. 결과를 본문 해시로 캐시하고 나서
# **기동이 1.9초**가 됐고, 그러자 재시작할 이유가 없어졌다.
#
# /reload 는 새 청크로 BM25 를 **먼저 짓고 그 다음에** 캐시를 비운다. 도는 동안
# 들어온 요청은 옛 인덱스로 정상 응답한다. sudo 도 필요 없다.
#
# 실패하면(-f 라서 4xx/5xx 에 0 이 아닌 코드) /tmp/index.log 에 남는다.
# 그때는 손으로: sudo systemctl restart bidmate-api
#
# **청크 파일 이름(CHUNKS)을 바꿨을 때만** 재시작이 필요하다. import 때 읽은
# 값을 쓰기 때문이다. 코퍼스 버전을 올릴 때 말고는 그럴 일이 없다.
#
# **증분이다.** 전처리는 지난번 전처리본을 캐시로 써서 새로 들어온 파일만
# 다시 뽑고, 색인은 lance 테이블에 새/바뀐 공고만 넣는다(`--sync`). 그래서
# 이 줄에 드는 시간은 코퍼스 크기가 아니라 **하루치**에 비례한다.
# 전처리 코드를 고쳤으면 캐시가 저절로 무효가 된다(모듈 mtime 을 본다).
